目标
  做一个“agent 进化器”：

  - 输入两个手工选择的 parent agent
  - 把它们解析成可遗传的 agentGene
  - 通过 crossover engine 做重组
  - 再做少量 mutation 修补
  - 输出新的 child agent
  - 对 child 做评估并记录 lineage

  ———

  一、先说清楚这套系统到底在干什么

  可以把它理解成一个“技能育种机”。

  普通的做法是：

  - 人直接写一份新 agent
  - 或者拿大模型让它“融合两个 agent”

  问题是：

  - 结果不可控
  - 不知道融合了什么
  - 失败了不能复盘
  - 没法稳定迭代

  所以我们把它工程化成 6 个步骤：

  1. 读取两个 parent agent
  2. 把 agent 解析成结构化基因 agentGene
  3. 用 crossover engine 重组基因
  4. 用 mutation 修补和微调
  5. 评估 child
  6. 保存 child、lineage、评估结果

  一句话：

  agent 是给人看的，Gene 是给系统重组的。

  四、核心概念定义

  1. agent
  最终给用户和 Agent 用的文档，比如 agent.md。

  它是“外壳”。

  2. agentGene
  从 agent 中提取出来的结构化遗传核心。

  它是“内核”。

  3. Crossover
  把两个 parent gene 的一部分按规则重组，得到 child gene。

  4. Mutation
  在 child gene 上做少量可控修改，解决断裂、冲突、冗余。

  5. Lineage
  记录 child 是怎么来的：

  - 哪两个 parent
  - 用了什么 crossover
  - 用了什么 mutation
  - 评估结果如何

  ## 五、agentGene 设计

  这是最重要的一层。

  ### 5.1 为什么要有 agentGene

  因为整份 agent 文档太松散，不适合重组。

  例如两份 agent 里都写了：

  - 使用场景
  - 工作流程
  - 工具约束
  - 输出格式
  - 验证方法

  如果直接拼 markdown，系统根本不知道：

  - 哪段是流程
  - 哪段是约束
  - 哪段是风格
  - 哪段应该继承自 A，哪段继承自 B

  所以要先把 agent 拆成“可遗传单位”。

  ———

  ### 5.2 agentGene 的人话理解

  你可以把一个 agent 想成一个“技能生物”，它体内有几类器官：

  - 它是干什么的：intent
  - 什么时候出场：trigger
  - 怎么做：workflow
  - 遇到分叉怎么判断：decision_rules
  - 能用什么工具：tool_policy
  - 产出长什么样：output_contract
  - 怎么证明自己做对了：validation
  - 什么不能做：anti_patterns
  - 说话风格：style_policy

  这些就是 gene 的组成部分。

  # 一、整体设计

  ## 1.1 这个系统到底在干什么

  可以把它想成“育种系统”：

  - `agent` 是成品说明书
  - `agentGene` 是 agent 的遗传骨架
  - `Crossover` 是把两个 parent 的优点重组
  - `Mutation` 是小范围变动，修复断裂或带来新特征
  - `Evaluation` 是看子代到底好不好用
  - `Lineage` 是族谱，记录孩子从哪来

  一句话：

  **不是直接把两份文档拼起来，而是先拆成结构化基因，再重组，再重新渲染成新 agent。**

  ---

  ## 1.2 系统边界

  这个版本先只做简单版：

  - parent 由用户手工选择
  - 核心放在 crossover
  - mutation 只做少量、受控的修补
  - evaluation 支持系统内置规则 + 用户自定义任务评分
  - 不做自动 parent 检索
  - 不做多代自动进化调度

  ---

  ## 1.3 总体流程

  ```text
  1. 读取 parentA / parentB 的 agent.md
  2. 解析为 agentGene
  3. 做兼容性检查
  4. 制定 crossover plan
  5. 生成 child gene
  6. 做 mutation 修补
  7. 做结构和一致性校验
  8. 渲染成 child agent.md
  9. 做评估
  10. 保存 child / lineage / mutation / evaluation

  # 二、核心概念

  ## 2.1 agent

  agent 是人看的成品文档。

  典型内容有：

  - 名称
  - 描述
  - 适用场景
  - 工作步骤
  - 工具规则
  - 输出格式
  - 验证方法
  - 禁止事项

  它适合阅读，不适合直接遗传。

  ———

  ## 2.2 agentGene

  agentGene 是 agent 的结构化、可重组表示。

  它不是一整篇文档，而是一组“基因位点”。

  你可以把它理解为：

  - 把 agent 拆成多个零件
  - 每个零件都可以单独继承、组合、修改
  - 最后再拼回一份完整 agent

  ———

  ## 2.3 Crossover Engine

  这是整个系统最关键的部分。

  它负责回答：

  - child 的哪一部分来自 A
  - 哪一部分来自 B
  - 哪些部分合并
  - 哪些部分必须保守处理
  - 合并后哪里断裂，需要怎么补

  它不是随机乱拼，而是按规则重组。

  ———

  ## 2.4 Mutation

  mutation 不是主角，但很重要。

  因为即使 crossover 做得好，两个 parent 拼起来后也常常会出现：

  - 步骤重复
  - 步骤顺序不顺
  - 工具规则冲突
  - 验证方法不匹配
  - 文风不一致

  mutation 在这个系统里的职责主要是：

  修补 crossover 造成的断裂，而不是胡乱创新。

  ———

  ## 2.5 Evaluation

  evaluation 负责判断：

  - child agent 是否结构完整
  - 是否逻辑自洽
  - 是否继承了双亲的有效部分
  - 是否真的比 parent 更有用

  # 四、agentGene 详细设计

  ## 4.1 设计原则

  agentGene 要满足 4 个要求：

  - 可解析：能从 agent 文档稳定提取
  - 可重组：字段能单独 crossover
  - 可验证：冲突容易检查
  - 可回渲染：能重新生成可读的 agent.md

  ———

  ## 4.2 agentGene 的主要结构

  建议用下面这套。

  ## 4.3 为什么这样拆

  这套拆法的重点是把 agent 分成两类：

  ### A. 适合重组的

  这些是 crossover 的重点：

  - workflow_gene
  - decision_gene
  - validation_gene
  - trigger_gene

  ### B. 适合保守合并的

  这些不适合大幅乱改：

  - tool_gene
  - safety_gene
  - output_gene

  ### C. 适合轻微调整的

  这些更多是修饰层：

  - style_gene
  - identity_gene

  ———

  ## 4.4 workflow_gene 为什么最重要

  因为一个 agent 的实际能力，大多体现在：

  - 先做什么
  - 后做什么
  - 遇到情况怎么分支
  - 最后如何验证

  所以 workflow_gene 是最主要的遗传对象。

  建议每个 step 都带 role，例如：

  - discover
  - analyze
  - plan
  - execute
  - validate
  - report
  - recover

  这样 crossover 才能按“角色对齐”而不是按段落拼接。

  ———

  # 五、Crossover Engine 详细设计

  ## 5.1 它的职责

  Crossover Engine 要完成 5 件事：

  1. 看两个 parent 哪些部分能拼
  2. 决定 child 各部分怎么继承
  3. 真正执行重组
  4. 检查是否出现断裂
  5. 输出 child gene 和 crossover 记录

  ———

  ## 5.2 先做兼容性检查

  在 crossover 前，先做简单兼容性检查，不兼容就直接拒绝或降级。

  建议检查：

  - intent 是否同域或近邻
  - workflow role 是否有重叠
  - tool policy 是否冲突过大
  - output contract 是否不可兼容
  - safety constraints 是否相互矛盾

  例如：

  - A 强制只读
  - B 强制必须写文件
    这种就不适合直接交叉

  可以给一个兼容性结论：

  {
    "compatible": true,
    "score": 0.74,
    "warnings": [
      "tool policy differs",
      "style differs"
    ]
  }

  ———

  ## 5.3 crossover plan 是什么

  在真正重组前，先生成一个计划。

  它相当于“遗传蓝图”。

  比如：

  {
    "identity_gene": "A",
    "trigger_gene": "merge",
    "workflow_gene": {
      "mode": "role_aligned",
      "mapping": {
        "discover": "A",
        "analyze": "A",
        "plan": "B",
        "validate": "B"
      }
    },
    "decision_gene": "merge",
    "tool_gene": "strict_merge",
    "output_gene": "A",
    "validation_gene": "merge",
    "safety_gene": "union",
    "style_gene": "A"
  }

  这样做的好处是：

  - 可解释
  - 可回溯
  - 可调试
  - 不会变成黑箱

  ———

  ## 5.4 推荐的 crossover 模式

  ## 模式 1：Section-level crossover

  最简单。

  每个大字段从 A/B 中选一个或合并。

  适合：

  - 先做 MVP
  - 便于解释
  - 成功率高

  缺点：

  - 创新度低
  - 容易只是 section 拼接

  ———

  ## 模式 2：Role-aligned workflow crossover

  推荐作为主模式。

  做法：

  - 把 A、B 的 workflow steps 按 role 分组
  - 对每个 role，选更优的一侧
  - 拼成 child workflow

  例子：

  Parent A：

  - discover 强
  - analyze 强

  Parent B：

  - plan 强
  - validate 强

  Child：

  - discover: A
  - analyze: A
  - plan: B
  - validate: B

  这是最稳的 crossover 方式。

  ———

  ## 模式 3：Prefix-suffix crossover

  也很实用。

  做法：

  - 前半流程继承 A
  - 后半流程继承 B

  适合：

  - A 擅长理解问题
  - B 擅长输出结果

  风险：

  - 中间接口容易断

  所以常常需要 mutation 加桥接步骤。

  ———

  ## 模式 4：Decision-rule merge

  这个必须单做。

  很多 agent 的精华是规则，不是步骤。

  比如：

  - “如果 dirty worktree，就不要做危险操作”
  - “如果仓库大，就先 search 再 read”
  - “如果用户没要求，不主动改代码”

  这些规则建议全部收集后：

  - 去重
  - 冲突检测
  - 保留更保守版本

  ———

  ## 5.5 具体重组规则

  ### identity_gene

  默认策略：

  - name: 重新生成
  - description: 重新总结
  - intent: 取主意图或最小公共上位意图

  不要直接把 parent name 拼起来。

  ———

  ### trigger_gene

  策略：

  - use_when: 合并去重
  - avoid_when: 合并去重
  - required_inputs: 取并集

  ———

  ### workflow_gene

  主战场。

  建议流程：

  1. 把 steps 标准化
  2. 按 role 对齐
  3. 选每个 role 的优胜 step
  4. 按依赖关系排序
  5. 检查是否缺桥接 step

  child workflow 输出时至少保证：

  - 顺序通
  - 依赖通
  - 没有明显重复
  - 每个关键 role 至少一个 step

  ———

  ### decision_gene

  策略：

  - 合并所有规则
  - 相同 condition 下保留更保守 action
  - 发现冲突则记 warning

  ———

  ### tool_gene

  策略必须保守。

  建议：

  - allowed_tools: 取交集或受限并集
  - forbidden_tools: 取并集
  - preferred_tools: 取并集后重排

  原则：

  权限只收紧，不轻易放宽。

  ———

  ### output_gene

  建议：

  - 如果两个 parent 输出格式差异不大，选更明确的那个
  - 如果差异很大，优先选用户更需要的那种
  - MVP 里可以直接继承 A 或 B，不强合并

  ———

  ### validation_gene

  建议：

  - 合并 success criteria
  - 合并 checks
  - 去掉重复和互相冲突项

  validation gene 很重要，因为它决定 child 是否可测。

  ———

  ### safety_gene

  策略：

  - constraints: 取并集
  - anti_patterns: 取并集

  安全规则宁可多一点，不要少一点。

  ———

  ### style_gene

  建议简单处理：

  - 选 A 或 B
  - 或做轻量归一化

  它不应该主导 child 的核心能力。

  ———

  # 六、Mutation 设计

  ## 6.1 mutation 的定位

  这个系统里 mutation 主要不是“随机创新”，而是“修复 crossover”。

  所以 mutation 应该在 crossover 之后运行。

  ———

  ## 6.2 推荐的 mutation operator

  ### 1. bridge_step_insert

  当 workflow 出现断层时，插入桥接步骤。

  例子：

  - A 的最后一步是“分析代码”
  - B 的第一步是“输出验证命令”
  - 中间缺“形成解决方案”

  就插入一个 bridge step。

  ———

  ### 2. redundancy_prune

  删除重复步骤。

  例子：

  - A、B 都有“search relevant files”
  - child 里重复了两次
  - 删除一个

  ———

  ### 3. consistency_repair

  修复字段不一致。

  例子：

  - workflow 说用 shell
  - tool_gene 禁止 shell
  - mutation 要么改 workflow，要么改 policy，但通常偏保守：改 workflow

  ———

  ### 4. validation_add

  如果 child 缺少验证闭环，自动补一个验证规则。

  ———

  ### 5. style_unify

  统一文风，让 child agent 更像一份完整文档，而不是拼接件。

  ———

  # 七、Evaluation 设计

  ## 7.1 先说结论

  是的，任务级评估最好允许使用者自己设计。

  但不代表全部都要用户设计。

  建议分两层：

  - 系统内置静态评估
  - 用户可选任务评估

  ———

  ## 7.2 系统内置静态评估

  这部分不用用户设计，系统自动做。

  ### 1. schema_score

  字段是否完整

  ### 2. consistency_score

  是否自洽

  - workflow 和 tool policy 是否一致
  - validation 是否与 output 对齐
  - trigger 和 intent 是否匹配

  ### 3. safety_score

  是否继承了必要安全约束

  ### 4. inheritance_balance_score

  是否真的继承了两个 parent，而不是只复制一个

  ### 5. novelty_score

  和 parent 是否有足够差异

  ———

  ## 7.3 用户任务评估

  这是最有价值的一层。

  因为 agent 的好坏高度依赖使用场景。

  建议允许用户给一个 EvaluationSpec：

  {
    "eval_name": "repo-analysis-agent-eval",
    "samples": [
      {
        "input": "分析这个仓库里认证失败的主要原因，并给出修复计划",
        "expected_properties": [
          "must_search_repo",
          "must_identify_related_files",
          "must_provide_risks",
          "must_include_validation"
        ]
      }
    ],
    "weights": {
      "task_success": 0.5,
      "format_compliance": 0.2,
      "safety": 0.2,
      "clarity": 0.1
    }
  }

  这样用户不需要写复杂代码，只要描述“好 agent 应该有什么表现”。

  ———

  ## 7.4 推荐 fitness 公式

  fitness =
    static_gate_pass
    ? 0.25 * consistency_score
    + 0.20 * safety_score
    + 0.15 * inheritance_balance_score
    + 0.10 * novelty_score
    + 0.30 * task_score
    : 0

  如果用户没有提供 task_score，可以暂时用默认 probe score 替代，但要标记为“弱评估”。

  ———

  # 八、输出资产设计

  每次进化建议保存 5 类东西。

  ## 8.1 child agent

  最终给人用的文档。

  ## 8.2 child gene

  真实的遗传结果。

  ## 8.3 lineage

  孩子怎么来的。

  {

  ## 8.4 mutation record

  记录做了哪些修补。

  ## 8.5 evaluation record

  记录 child 得分和是否接受。

  # 九、普通人能理解的例子

  假设有两个 parent。

  Parent A
  擅长：

  - 搜索代码库
  - 找相关文件
  - 看调用链

  Parent B
  擅长：

  - 输出修复计划
  - 写风险说明
  - 给验证步骤

  你想生成一个 child：
  “既会分析代码库，又会给出安全修复计划”

  流程就是：

  1. 系统把 A、B 拆成 agentGene
  2. 发现：

  - A 的 discover/analyze 强
  - B 的 plan/validate 强

  3. crossover plan 定成：

  - 前半继承 A
  - 后半继承 B

  4. child gene 初稿出来后发现：

  - 从“分析代码”直接跳到“验证计划”，中间少了“形成修复方案”

  5. mutation 插入 bridge step：

  - “基于分析结果，整理 2-3 个修复方案”

  6. 再检查工具规则和输出格式
  7. 生成 child agent.md
  8. 打分，看它是否比单独 A 或 B 更完整

  这就是“有基因概念的 agent crossover”。

  ———

  # 十、MVP 建议

  第一版不要太复杂，建议只做这些：

  ## 必做

  - agent -> agentGene parser
  - agentGene schema
  - compatibility check
  - role-aligned workflow crossover
  - decision merge
  - conservative policy merge
  - 3-5 个 repair mutation
  - static evaluation
  - render child agent

  ## 先不做

  - 自动 parent 检索
  - 多代种群进化
  - 复杂语义 crossover
  - 自主学习评分器
  - 自动上线 child

  ———

  # 十一、模块接口建议

  ## parser

  - parseagent(agentPath) -> agentGene
  - renderagent(gene) -> agentMarkdown

  ## compatibility

  - checkCompatibility(geneA, geneB) -> CompatibilityReport

  ## crossover planner

  - buildCrossoverPlan(geneA, geneB, options) -> CrossoverPlan

  ## crossover engine

  - crossover(geneA, geneB, plan) -> ChildGeneDraft

  ## mutation

  - repairChildGene(childDraft) -> { childGene, mutations }

  ## evaluation

  - runStaticEval(childGene) -> StaticEvalReport
  - runTaskEval(childagent, evalSpec?) -> TaskEvalReport
  - computeFitness(staticEval, taskEval) -> FitnessReport

  ## pipeline

  - evolve(parentAPath, parentBPath, options) -> EvolutionResult

  ———

  # 十二、一句话收束

  这套进化器最合理的实现方式是：

  把 agent 当作文档，把 gene 当作真正参与遗传的结构；把 crossover 当作主引擎，把 mutation 当作修复器，把 evaluation 当作筛选
  器。
